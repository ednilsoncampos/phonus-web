Veja a discussao no backend:
Login já funciona hoje, independente da matriz. Como vimos, loadUserByUsername resolve o tenant e autentica via usuario_global + usuario, sem passar por @PreAuthorize. O SUPER_ROOT já consegue logar e receber um JWT válido. O que falta na matriz não bloqueia o login — bloqueia tudo que vem depois, a começar pelo próprio GET /auth/me. Então hoje o SUPER_ROOT "loga" (ganha token) mas não consegue chamar nenhum endpoint protegido, nem o /auth/me — do ponto de vista de quem usa o app, isso parece login quebrado, mas tecnicamente é autorização.
Sobre o redirecionamento do front por permissão: sim, é exatamente assim que o sistema foi desenhado. O CLAUDE.md já documenta isso: GET /auth/me expõe UsuarioResponse.permissoes[] — a mesma matriz que os @PreAuthorize usam no backend — "front consome essa lista em vez de reimplementar a tabela de papéis". Ou seja, a tela pós-login não deveria ter um if (papel == "ROOT") ... else if (papel == "ADMIN") fixo; ela deveria olhar o array permissoes retornado e decidir o que mostrar/pra onde mandar o usuário com base nisso.
O ponto prático: se eu só adicionar SUPER_ROOT em CONTA_PROPRIA, o /auth/me passa a responder, mas o array permissoes dele vai conter só ["TERMOS_GERENCIAR", "CONTA_PROPRIA"] — nada de FINANCEIRO_CONSULTAR, USUARIOS_GERENCIAR, etc. Então o front, seguindo a própria lista, não deveria redirecionar o SUPER_ROOT pro dashboard normal da empresa (caixa, lançamentos, usuários) — ele não tem acesso a nada disso hoje. O destino natural seria uma tela de administração de termos de uso (ou uma tela de perfil/landing mínima), já que é o único recurso que a matriz libera pra esse papel.

Abaixo sao as mudanças do backend
- MatrizPermissoes.kt: CONTA_PROPRIA agora inclui EnumPapel.SUPER_ROOT — corrige o 403 no /auth/me visto no log. SUPER_ROOT continua sem FINANCEIRO_CONSULTAR, USUARIOS_GERENCIAR, CADASTROS_* etc. (escopo aprovado: só conta própria + termos de uso).
- MatrizPermissoesTest.kt: novo teste travando esse contrato (SUPER_ROOT tem CONTA_PROPRIA, não tem os recursos de empresa).
- CLAUDE.md: nota explicando que a hierarquia (podeGerenciar) não implica herança de recursos na matriz, e que o front deve usar permissoes[] de /auth/me para decidir o redirecionamento pós-login — não só o papel.
- docs/api-reference-mobile.md: adicionada a linha do SUPER_ROOT na tabela de papéis, deixando explícito para quem for construir a tela web que ele precisa de um destino próprio (ex.: administração de termos), não o dashboard normal da empresa.
